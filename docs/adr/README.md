# Architecture Decision Records

ADRは、重要な設計判断について、背景・比較案・採用理由・影響・人間の承認を残す記録です。
このリポジトリでは運用ガイドと [テンプレート](template.md) を提供します。テンプレート自体は採用済みの判断ではありません。

## 記録する対象

- 構成要素の責務や、依存方向の決定・変更。
- データベース、主要な技術・外部依存の選定。
- 公開インターフェースやデータモデルの重要な決定・変更。
- 性能・信頼性・セキュリティなどに関わる重要な設計上のトレードオフ。

誤字修正、既存仕様内の小さな不具合修正など、既存アーキテクチャに影響しない軽微な変更には新たなADRや設計承認は不要です。

## 作成と承認

1. 適用先プロジェクトで `template.md` をコピーし、`0001-choose-database.md` のような連番と内容の分かるファイル名を付けます。番号は再利用しません。
2. 1件につき1つの重要な設計判断を扱い、状態を `Proposed` にします。生成AIは下書き・比較案の整理を担当できます。
3. 人間と設計を検討し、背景、比較案、採用理由、決定内容、良い影響と不利益を具体化します。短く読める分量を目安とします。
4. 人間が明示的に承認した場合だけ `Accepted` にし、承認者・承認日をADRに記録します。生成AIは承認を推測せず、コミットやマージだけを承認の根拠にしません。
5. `TASKLIST.md` から関連ADRを参照し、承認された判断に依存する重要な実装に着手します。承認前でも調査・設計検討・計画作成は進められます。
6. 実装・検証の進捗は `TASKLIST.md` に記録し、現在の構成や使い方が変わった場合はプロジェクトの `README.md` を更新します。

既存プロジェクトへ導入する場合は、現在の構成を調べた記録と、人間が承認した判断を区別してください。過去の承認者や承認日を推測で埋めず、新たな判断が必要な箇所から運用を始めます。

## 状態

| 状態 | 意味 |
| --- | --- |
| `Proposed` | 検討中。人間の承認前。 |
| `Accepted` | 人間が承認した判断。実装完了を意味しない。 |
| `Rejected` | 採用しなかった提案。理由を残す。 |
| `Superseded` | 後継の採用済みADRによって置き換えられた判断。 |

## 判断を変更する場合

- 採用済みADRの判断内容を、後から別の結論に書き換えません。新しいADRを作り、変更の背景と理由を説明して人間の承認を得ます。
- 後継ADRには置き換えるADRへのリンクを記載し、元のADRには `Superseded` と後継ADRへのリンクを記録します。元の判断の背景や理由は残します。
- 誤字・参照先の修正、状態や置き換え関係の更新は可能です。

## 他の文書との役割分担

| 文書 | 管理する内容 |
| --- | --- |
| 各ADR | 設計判断、背景、比較案、採用理由、影響、承認情報の正本。 |
| プロジェクトの `README.md` | 現在の構成・使い方と、関連ADRへのリンク。 |
| `TASKLIST.md` | 作業計画・進捗・残課題・検証結果の唯一の正本。 |

承認情報をREADME・TASKLIST・一覧に再記入せず、各ADRを参照します。ADRの承認状態と実装状況は別々に確認してください。

## ADR一覧

適用先でADRを作成したら、ここに番号・タイトル・ファイルへのリンクを追記します。状態と承認情報は各ADRを参照してください。

まだ設計判断のADRはありません。
